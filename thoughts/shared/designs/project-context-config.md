# 项目背景配置设计方案

> 起草日期：2026-05-13
> 起草人：Damon

## 一、设计背景与目标

当前 AI 洞察在分析项目销售数据时，缺少业务上下文。运营人员上传数据后，AI 只能看到冷冰冰的数字，无法判断：

- 销量增长是"运营做得好"还是"淡季低价清仓"
- 库存积压是"选品失误"还是"工厂产能跟不上"
- 广告投放效果差是"素材问题"还是"淡季整体转化率低"

**目标**：在数据库中记录项目背景信息，让 AI 在生成洞察时能够结合业务实际情况做出准确判断。

---

## 二、数据层设计

### 2.1 存储策略

采用 **JSON 字段** 存储，而非固定结构字段。

设计理由：
- 每个项目独特性高，不存在固定模板
- 业务维度可能随时间增加和演变
- 结构化字段会导致表结构频繁变更
- JSON 可兼顾结构化维度（供 AI 解析）和自由文本（供运营填写）

### 2.2 字段设计

在 `projects` 表新增两个 JSON 字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `project_context` | JSON | 项目级背景信息（工厂供货、产品周期、项目状态等） |
| `sku_context` | JSON | SKU 级特殊状态（清仓、秒杀、停产等） |

### 2.3 JSON 结构定义

#### project_context

```json
{
  "factory": {
    "description": "工厂位于深圳宝安，标准交货周期 15 天，淡季可压缩至 10 天",
    "productionCapacity": "月产能 5000 件，旺季峰值 8000 件",
    "communication": "对接人张工，响应速度快，品质稳定"
  },
  "productSeasonality": {
    "peakSeason": "Q4（10-12 月）销量占全年 45%",
    "offSeason": "Q2（4-6 月）为淡季，建议控制库存水位",
    "restockStrategy": "旺季前 45 天开始备货"
  },
  "productGrowth": {
    "description": "产品处于增长期，2024 年同比增长 30%",
    "growthDriver": "主要依靠新品迭代，非促销驱动"
  },
  "projectStatus": {
    "description": "2024 年 10 月新开项目，目前处于爬坡期",
    "riskNotes": "广告 ACOS 偏高，正在优化中"
  }
}
```

#### sku_context

```json
{
  "SKU-BB001": {
    "status": "清仓处理",
    "reason": "库龄超过 270 天，资金积压",
    "action": "限时折扣 30%，目标一个月内清空",
    "startDate": "2024-01-15"
  },
  "SKU-BB002": {
    "status": "秒杀活动",
    "reason": "新品推广期，冲刺排名",
    "action": "站外引流配合，折扣 20%",
    "endDate": "2024-02-28"
  }
}
```

### 2.4 Key 命名说明

- **英文 Key**：JSON key 使用 English camelCase（如 `factory`、`productSeasonality`）
- **原因**：英文 key 更通用，便于 AI 解析，也避免编码问题
- **中文 Value**：所有内容（description、reason 等）均使用中文书写，便于运营人员理解和编辑

### 2.5 维度定义

| 维度 | Key | 说明 |
|------|-----|------|
| 工厂供货 | `factory` | 工厂信息、生产能力、备货周期、沟通协作 |
| 淡旺季 | `productSeasonality` | 高峰期、淡季、备货策略 |
| 产品增长 | `productGrowth` | 增长性质（新项目/增长期/成熟期） |
| 项目状态 | `projectStatus` | 当前阶段、风险提示 |
| SKU 特殊状态 | sku_context (顶层 Key 为 SKU) | 清仓、秒杀、停产等 |

## 三、后端设计

### 3.1 数据库迁移

新增两个 JSON 字段：

```sql
ALTER TABLE projects ADD COLUMN project_context JSONB DEFAULT '{}';
ALTER TABLE projects ADD COLUMN sku_context JSONB DEFAULT '{}';
```

可选：添加 GIN 索引提升查询性能（如果后续需要按 context 内容查询）。

### 3.2 API 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/v1/projects/{id}/context` | 获取项目背景配置 |
| `PATCH` | `/api/v1/projects/{id}/context` | 更新项目背景配置（JSON Merge Patch 语义） |
| `GET` | `/api/v1/projects/manage` | 列表接口新增 `has_context` 布尔标识 |

#### GET /api/v1/projects/{id}/context

响应示例：

```json
{
  "project_id": 1,
  "project_name": "宝勒3店",
  "project_context": {
    "factory": {
      "description": "工厂位于深圳宝安..."
    },
    "productSeasonality": {
      "peakSeason": "Q4 为旺季..."
    }
  },
  "sku_context": {
    "SKU-BB001": {
      "status": "清仓处理"
    }
  }
}
```

#### PATCH /api/v1/projects/{id}/context

请求体（支持部分更新）：

```json
{
  "project_context": {
    "factory": {
      "description": "更新后的工厂说明"
    }
  },
  "sku_context": {
    "SKU-BB003": {
      "status": "停产",
      "reason": "供应链问题"
    }
  }
}
```

### 3.3 服务层修改

`project_service.py` 新增函数：
- `get_project_context(db, project_id)`
- `update_project_context(db, project_id, project_context, sku_context)`

### 3.4 AI 注入逻辑

修改 `ai_insight_aggregator.py` 的 `aggregate_project_data()` 函数：

```python
def aggregate_project_data(
    db: Session,
    project_id: int,
    country: str,
    start_date: date,
    end_date: date,
    progress_cb: ProgressCallback | None = None,
) -> AggregatedData | None:
    # ... 现有逻辑 ...

    # 新增：读取项目背景信息
    project_context, sku_context = project_service.get_project_context(db, project_id)

    return AggregatedData(
        # ... 现有字段 ...,
        project_context=project_context or {},
        sku_context=sku_context or {},
    )
```

修改 `AggregatedData` dataclass，新增两个字段：

```python
@dataclass
class AggregatedData:
    project_name: str
    country: str
    date_range_start: date
    date_range_end: date
    sales_by_date: list[dict[str, Any]] = field(default_factory=list)
    # ... 现有字段 ...
    project_context: dict[str, Any] = field(default_factory=dict)  # 新增
    sku_context: dict[str, Any] = field(default_factory=dict)      # 新增
```

## 五、AI 洞察注入设计

### 5.1 注入时机

在 `ai_insight_generator.py` 的系统 Prompt 中增加项目背景信息章节。

### 5.2 注入位置

修改 `INSIGHT_SYSTEM_PROMPT`：

```
## 项目背景信息（运营人员提供）

以下是该项目运营人员提供的背景信息，生成洞察时请结合这些信息进行分析：

### 项目背景
{fetched_project_context_formatted}

### SKU 特殊状态
{fetched_sku_context_formatted}

---

请根据以上数据生成洞察报告。
```

### 5.3 格式化示例

```
### 项目背景
- **工厂供货**：工厂位于深圳宝安，标准交货周期 15 天，淡季可压缩至 10 天；月产能 5000 件，旺季峰值 8000 件；对接人张工，响应速度快，品质稳定
- **淡旺季**：Q4（10-12 月）为旺季，销量占全年 45%；Q2（4-6 月）为淡季，建议控制库存水位；旺季前 45 天开始备货
- **产品增长**：产品处于增长期，2024 年同比增长 30%，主要依靠新品迭代，非促销驱动
- **项目状态**：2024 年 10 月新开项目，目前处于爬坡期；广告 ACOS 偏高，正在优化中

### SKU 特殊状态
- **SKU-BB001**：清仓处理。库龄超过 270 天，资金积压。行动：限时折扣 30%，目标一个月内清空
- **SKU-BB002**：秒杀活动。新品推广期，冲刺排名。行动：站外引流配合，折扣 20%
```

### 5.4 AI 分析指导

在系统 Prompt 中增加约束：

```
## 背景信息使用规则

生成洞察时必须遵循以下规则：
1. **销量异常解读**：如果某 SKU 正在清仓或做活动，其销量增长应归因于促销而非自然增长
2. **淡旺季判断**：Q4 销量高于 Q2 是正常季节性表现，不应作为运营评价依据
3. **风险标注**：如果发现数据与背景信息矛盾（如背景说"产能充足"但库存经常断货），需在洞察中特别指出
4. **库存建议**：结合备货周期信息，判断当前库存水位是否合理
```

## 七、注意事项

### 7.1 数据兼容性

- 如果 `project_context` 或 `sku_context` 为空，AI 洞察生成时应跳过相关章节
- 字段更新使用 JSON Merge Patch 语义，只更新传入的字段

### 7.2 性能考虑

- JSON 字段避免存储过大的内容（建议每个字段不超过 64KB）
- 如果需要按 context 内容查询，添加 GIN 索引

### 7.3 未来扩展

- 可以在 `project_context` 中增加 `tags` 数组字段，用于快速标记项目类型（如"新品"、"清仓"、"旺季冲刺"）
- 可以考虑为 SKU context 增加 `effectiveDate` 和 `expiryDate` 字段，自动判断状态是否生效
