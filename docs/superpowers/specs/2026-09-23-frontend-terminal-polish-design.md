# 前端登录页重做与 Terminal 体验打磨设计

## 背景与目标

BelieveBoy Dashboard 已形成现行 V3 Terminal 设计体系，擅长高密度业务数据呈现。当前登录页仍采用带圆角和阴影的终端窗口式卡片，与正式后台的零圆角、零阴影、1px 边界规范存在视觉落差。用户希望对登录页全新重做，并系统打磨正式页面的组件细节与动效。

> **状态：** 设计草案，待用户复核。**范围：** 本文只定义登录页重做与正式后台分批打磨方向，不包含实现步骤。

本设计分成两个相互关联但可分批交付的方向：

1. 登录页作为完整入口重新组织品牌表达、视觉层级和认证表单。
2. 正式后台在 V3 Terminal 视觉权威内，按系统层级逐步完善外壳、通用组件、代表页面和其余模块的呈现与动效。

## 已确认的产品事实与约束

- 主要用户是跨境电商多品牌运营团队成员。
- 产品提供运营中台与终端式高密度数据工作区。
- 登录品牌可使用 BelieveBoy / 彼励扶跨境。
- 不得虚构客户案例、客户背书、业务成效、性能数字或未确认的在线服务状态。
- 正式后台继续遵循 `frontend/docs/design-spec.md` 中的 V3 Terminal 规范：零圆角、零阴影、1px 边界、mono 数值、`--term-*` 明暗双主题，以及共用控件尺寸档位。主页 dashboard-v2 属于已登记的刻意例外；具体页面打磨范围需先核对例外条目与现状，不能顺手重做该体系。
- 认证方式与行为保持现状：账号密码、NextAuth credentials、callback 跳转及其安全限制、错误处理、提交状态、密码可见性、主题切换。
- 动效遵循 `frontend/docs/motion-system.md` 与现有 primitives/tokens；支持 reduced-motion / reduced-transparency，并遵守性能预算。
- 覆盖桌面和移动布局，不改变业务数据语义和权限行为。

## 方向一：登录页——品牌主视觉 + 终端登录区

登录页是 BelieveBoy 正式工作区的入口（Operate）。以重新组织的品牌主视觉确立产品识别，同时让账号密码认证成为第一眼可见、可操作的主任务。不是缩小版后台，也不是单纯换皮的终端卡片。

- 重构当前登录页的页面构图和信息层级，保留真实品牌名称与已经确认的产品定位。
- 认证表单作为主操作区；桌面采用清晰的品牌/表单关系，移动端改为单列并优先保证表单可见和易触达。
- 保留明暗主题体验和现有登录状态反馈；失败信息靠近表单且不造成布局跳动。
- 保留浏览器密码管理器兼容性、正确的表单语义、键盘可操作性与焦点可见性。
- 移除或改写会被误读为实时监控事实的静态 boot 状态文案；只展示有事实依据的内容。
- 样式与品牌细节仍服从 V3 Terminal 设计纪律，不能重新引入圆角面板、阴影或第三套色彩 token。
- 登录进场动效克制而有辨识度；认证等待、成功跳转和错误态使用明确反馈，不延迟用户完成登录。

## 方向二：正式后台——系统优先、逐批扩展

按以下顺序建立一致性，避免在每个页面重复修补同一类问题：

1. **Terminal 外壳**：检查 Rail、SubNav、Header、Inspector、Footer 的对齐、密度、图标/文字层级、交互状态和移动导航；遵循 `terminal-constants.ts` 与既有尺寸/排版阶梯。
2. **共用高频组件**：优先审视按钮、输入与选择类、Tabs、面板、表格、状态标记，以及 loading/empty/error/success 状态。保留各组件现有 API 与业务语义，视觉统一优先通过原子组件和共享原语实现。
3. **代表性页面样板**：以运营分析/报表等高密度、高频场景验证布局、筛选、表格/图表、状态反馈与主题适配；首页列为候选，但需先依据已登记的 dashboard-v2 例外确认适用范围。具体先后顺序在实施计划里结合路由使用频率和组件影响面排定。
4. **按模块扩展**：从样板中沉淀规则，按模块推进；同类页面批量复核，避免全仓一次性大改带来高回归风险。

### 动效原则

- 加强路由进入、侧栏/Inspector 开合、筛选和 Tab 状态变化、刷新/异步状态、成功/错误反馈等与任务相关的动效。
- 动效允许更具表现力，但不可遮挡数据、拖延关键操作、诱发持续分心或依赖昂贵的全局指针监听。
- 优先复用 `components/motion/*` 与现有 `--motion-*` / JS token。确需新增或调整 token 时，CSS 与 JS 镜像同步，并补相应验证。
- 对 `prefers-reduced-motion` 与 `prefers-reduced-transparency` 做一致退化；触摸设备不依赖 hover 才能获取状态信息。

## 交互状态与响应式要求

- 登录页至少覆盖初始、输入校验、提交中、认证失败/网络失败、成功跳转以及明暗主题状态。
- 通用组件打磨覆盖默认、hover、focus-visible、active、disabled、loading，以及适用的 empty/error/success 状态。
- 桌面保留高效终端式密度；移动端优先保障关键任务、触控命中区、内容顺序及横向溢出控制。
- 重要内容默认可见；不以入场动画隐藏核心信息。

## 不在本设计范围内

- 更换认证方式、增加注册/找回密码/单点登录流程。
- 改动后台业务流程、权限控制、API 或数据展示含义。
- 未经确认重写产品事实、增加营销承诺、客户案例或数据指标。
- 无差别为所有页面添加装饰性动画，或全量替换已经有效的设计令牌与组件 API。

## 验收原则

- 登录页在常见桌面与移动视口下，品牌识别、认证主操作、错误反馈和主题状态均清晰；现有认证和 callback 行为完整保留。
- 正式后台的外壳和共用组件遵循已记录的 V3 Terminal 规范，无圆角/阴影回归、主题缺色或尺寸档位漂移。
- 动效明确表达状态和层级，不影响数据阅读；减少动态偏好下无非必要运动。
- 相关单元测试、设计/响应式/无障碍/动效测试与项目标准 lint、build、test 检查通过；实施阶段按变更范围选择端到端回归。
- 通过一次桌面与移动的批量视觉检查，并在一轮集中修正后复核；保留剩余问题供后续模块批次处理。

## 实施分批建议

- **第一批**：登录页完整重做与行为回归。
- **第二批**：Terminal 外壳细节和共享交互/动效基线。
- **第三批**：高频共用组件状态覆盖。
- **第四批及后续**：首页、运营分析/报表代表页验证，再按业务模块扩展。
