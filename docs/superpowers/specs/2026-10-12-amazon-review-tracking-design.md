# Amazon 商品评分与评论历史追踪设计探索

- 日期：2026-10-12
- 状态：阶段 A 已完成；阶段 B–D 待后续设计与实施
- 相关：[`2026-10-12-amazon-review-tracking-phase-a.md`](../plans/2026-10-12-amazon-review-tracking/2026-10-12-amazon-review-tracking-phase-a.md)
- 范围声明：本文记录已确认的业务方向、数据概念和待后续确认事项。阶段 A 已实现 SKU info Father ID 与内部评论共享组配置的后端基础；评分快照、Review 数据、运营页面和 Agent API 尚未实施。本稿不代表后续阶段实施方案已定稿。

## 1. 背景与目标

目前已通过浏览器验证 Amazon 商品页面能够读取商品评分汇总、星级分布及部分评论详情。后续希望按日跟踪多个 ASIN 的数据变化，并长期保留历史，以便观察商品口碑变化、发现问题和支持产品升级复盘。

目标包括：

- 按 ASIN 和站点记录每日评分与评论数量快照，不覆盖已有历史。
- 展示平均评分、评分总数、评论数和星级分布的时间变化。
- 在图表 hover 时查看对应日期的具体评分与各星级详情。
- 保存可获取的逐条 review 内容及其属性，并支持后续去重与变化追踪。
- 能区分页面实际提供的数据、解析得到的数据和推算数据。

## 2. 范围与非目标

**本次讨论范围：**

- 每日评分快照的概念字段。
- 逐条 review 的概念字段及历史观察需求。
- 图表查询与 hover 展示需求。
- 数据准确性、身份标识、采集缺失和长期保留方面的注意事项。

**当前非目标：**

- 不决定使用何种 Amazon 页面采集方式、第三方服务或 API。
- 不决定定时任务、重试、告警、部署或权限实现。
- 不确定首批 ASIN 范围、市场范围和上线时间。
- 不把 Amazon 页面上未提供或无法稳定提取的字段当作必备数据。
- 不把由页面百分比反推的星级数量当作精确统计。

## 3. 数据概念

建议将商品级聚合指标与单条评论分开考虑。以下是需求层面的字段候选，不是已定数据库表结构。

### 3.1 每日商品评分快照

每个 ASIN、Marketplace 和抓取日期保留一份快照。若同一天需要多次抓取，也应保留实际抓取时间，以便区分日级业务口径与原始观测记录。

| 字段概念 | 说明 |
| --- | --- |
| `asin` | Amazon 商品标识。 |
| `marketplace` | 站点标识，例如 `US`；同一个 ASIN 在不同站点需分别跟踪。 |
| `captured_at` | 实际抓取时间，建议保存带时区的时间戳。 |
| `capture_date` | 按约定时区归属的业务日期，用于日趋势查询。 |
| `average_rating` | 页面展示的平均评分，例如 2.6 / 5。 |
| `rating_count` | 页面展示的评分总数，例如 “7 global ratings”。它不等同于有正文的 review 数。 |
| `review_count` | 可获取的有正文 review 总数；若页面未可靠提供，应为空而不是用 `rating_count` 替代。 |
| `star_1_percentage` … `star_5_percentage` | 页面展示的各星级百分比，作为原始页面值保存。 |
| `star_1_count` … `star_5_count` | 各星级数量。只有来源能提供精确值时才标记为精确；由百分比推算时必须记录为估算值。 |
| `star_count_quality` | 星级数量口径，例如 `exact`、`estimated`、`unavailable`。 |
| `source` | 数据来源或采集方式标识，用于溯源。 |
| `capture_status` | 抓取结果状态，区分成功、部分成功、失败等情况。 |
| `raw_payload` | 可选，保存必要的原始解析结果，供排查页面变化或解析错误使用。 |

快照的逻辑唯一性需在后续设计中决定：可以是 ASIN、Marketplace、业务日期，也可以允许同日多次观测并以 `captured_at` 区分。无论采用哪种方案，都应避免新数据覆盖旧历史。

### 3.2 单条 review

逐条评论应独立保存，优先使用来源提供的稳定评论标识进行去重。用户提出的 user ID 应尽量采集，但需要接受页面可能不提供稳定 ID 的情况。

| 字段概念 | 说明 |
| --- | --- |
| `asin`、`marketplace` | 评论所属商品和站点。 |
| `review_id` | 来源提供的稳定评论标识；无法获取时需另行定义有限可靠的去重策略。 |
| `reviewer_id` | 页面或评论元数据中可取得的用户标识；无法取得时为空。 |
| `reviewer_name` | 页面展示的评论者昵称，仅作展示信息，不作为稳定身份键。 |
| `rating` | 该条评论对应的星级。 |
| `title` | 评论标题；页面无标题时为空。 |
| `body` | 评论正文。 |
| `review_date` | 页面展示的评论日期；应明确保存原始日期和后续标准化的日期口径。 |
| `verified_purchase` | 是否标记为 Verified Purchase。未知状态与 `false` 应能区分。 |
| `helpful_vote_count` | 有帮助票数；仅在页面可获取时记录。 |
| `first_seen_at` | 系统首次观察到该评论的时间。 |
| `last_seen_at` | 系统最近一次观察到该评论的时间。 |
| `last_seen_status` | 最近一次采集中的状态，例如仍可见、疑似缺失或已确认移除；不应仅凭一次未抓到就认定删除。 |
| `raw_payload` | 可选，保留与解析相关的原始字段，注意控制敏感信息和存储范围。 |

用户 ID、昵称和评论 ID 是不同概念：昵称可能重复或变化，不能代替 `reviewer_id`；评论 ID 也不能用于识别评论者。

### 3.3 可选的 review 观察历史

若只需保留评论文本及首次/最近发现时间，可先以单条 review 记录为中心；若后续需要还原评论编辑、评分变化、Verified Purchase 状态变化或 helpful votes 变化，则需增加按抓取时间记录的 review observation 历史。是否保留每次观察的完整正文、仅记录变更，或采用其他策略，待数据量、用途和保留要求明确后再决定。

## 4. 数据口径与质量约束

1. **Ratings 与 reviews 不等价。** Amazon 的 global ratings 可能包含只打星、没有文字评论的评分；评分总数和有正文的 review 数应分开保存。
2. **星级百分比可能经过舍入。** 不能仅用百分比乘以总评分数并将结果当成精确星级计数。应保留原始百分比，并记录数量是否精确、估算或不可得。
3. **用户标识可能不可得。** 评论者昵称不稳定且可能重复；若无法提取稳定用户 ID，应保留空值，不应自行推断身份。
4. **缺失不代表删除。** 页面分页、筛选、排序变化、临时采集失败或评论不可见，都可能导致一次抓取没有出现某条评论。确认删除需要明确规则和足够证据。
5. **区分空值与零。** 未提供、未解析到、采集失败与真实为 0 是不同状态；数据模型和图表口径应能表达这些差别。
6. **保存来源和时间。** 记录 Marketplace、采集时间、日界线采用的时区、来源及采集状态，以便解释跨站点或跨日差异。
7. **长期留存需定义治理规则。** 评论正文与用户相关字段可能涉及隐私、使用条款和保留限制；在定实施前需确认可采集范围、访问权限、保留期限及删除流程。

## 5. 图表与查询需求

未来图表至少需要支持：

- 按 ASIN、Marketplace 和日期范围筛选。
- 查看平均评分、`rating_count`、可用的 `review_count` 和星级分布随时间的变化。
- hover 展示对应快照的日期、平均评分、总评分数、评论数、1–5 星的页面占比，以及各星级精确数量或估算数量的口径标识。
- 对缺失日期、抓取失败或部分成功明确呈现，避免把缺测误认为数量不变或归零。
- 从某个时间点进入对应评论列表，查看该时点已观察到的 review 及其星级、日期、正文和 Verified Purchase 状态（具体交互待定）。

图表应从不可变的历史快照查询，而不是只读取商品表中的最新评分字段。长期数据量、索引、分区或归档策略应在预计 ASIN 数、评论数量和保留期限明确后再设计。

## 6. 浏览器验证样例

验证商品：[Amazon ASIN B0G6C865B6](https://www.amazon.com/dp/B0G6C865B6)

2026-10-12 页面读取到以下示例数据：

- 平均评分：2.6 / 5。
- Global ratings：7。
- 星级占比：5 星 16%、4 星 16%、3 星 15%、2 星 16%、1 星 37%。
- 评论区可见评论者展示名称、星级、标题、评论日期、Verified Purchase 标记和正文；部分评论还显示 helpful 信息。
- 本次页面没有确认稳定的评论者 user ID，也没有取得可作为持久去重键的 review ID。

页面只展示星级百分比而未直接展示每个星级的绝对数量。基于 7 条评分反推的星级数仅是估算，不应写成精确值。页面内容会随时间变化；以上数据只用于说明字段形态，不作为未来抓取结果的固定基准或业务结论。

## 7. 待确认问题

在形成正式设计或实施计划前，需要讨论并决定：

1. 首批追踪哪些 ASIN、Marketplace 和商品；由谁维护追踪清单？
2. 页面数据采集是否符合适用的 Amazon 条款、授权范围和内部合规要求？采用何种获准数据来源？
3. 每日抓取的时间、时区、失败重试、部分成功和告警口径是什么？
4. 评论采集采用全量、分页增量还是有限窗口；如何发现新增、编辑和不可见评论？
5. 实际页面或数据来源能否稳定提供 review ID、reviewer ID、星级绝对数量和 review 总数？若不可得，产品如何展示缺失或估算？
6. 评论首次出现后是否长期保存正文？用户相关信息的访问权限、保留期限和删除要求是什么？
7. 评论在页面上消失时，经过几次成功采集或何种证据后，才标记为疑似/确认移除？
8. 是否需要保存每次 review 观察，以追踪正文编辑和 helpful votes 的变化？
9. 是否需要对历史数据做回填？从哪个日期开始，如何标注数据来源和可信度？
10. 图表的日期归属、星级分布口径、缺失数据呈现和“评论数”定义是什么？
11. 数据规模达到什么预期后，需要制定归档、分区或冷热存储策略？
12. 是否需要通知、异常阈值、权限控制、审计和导出能力？

## 8. 已确认的产品方向与阶段边界

以下内容是在需求讨论中确认的产品方向，后续正式设计需以此为基础：

### 8.1 商品来源与关系

- 内部商品来源于 Project 下的 SQ info；父子 ASIN 关系在 SKU info 中维护。
- 父子关系由运营人员手动填写 Father ID。具体 Father ID 与现有 SKU info / ASIN 数据的关联方式，需在阶段 A 调研后确定。
- 评论共享组由运营人员在 SKU info 中配置；内部组的代表 ASIN 由运营人员手动指定。
- 父子关系和评论共享组是不同概念。同一父体允许存在多个评论共享组，以支持父体下的 ASIN 分别呈现不同评分或评论数据。
- 关系调整后不自动合并或拆分历史。旧数据留在原组；如需迁移，由未来的人工功能明确处理。

### 8.2 外部竞品

- 外部竞品 ASIN 只在「评论追踪」页面中作为临时记录，关联到指定店铺，不进入 SKU info，也不作为需维护的内部商品主数据。
- 外部 ASIN 默认每个 ASIN 单独成组；除非运营人员明确配置共享关系。
- 同一个 Marketplace + ASIN 只保留一份追踪数据。外部竞品可关联多个店铺，关联关系与 ASIN 及其历史分开保存。
- 移除店铺关联时只做状态标记并保留数据。之后重新添加同一 ASIN 与同一店铺关联时，恢复原关联并沿用历史，不重复创建追踪历史。

### 8.3 采集与历史

- Agent 优先调用系统 API 获取当前有效的共享组、代表 ASIN、Marketplace 和抓取规则，再执行采集；内部商品目标由 SKU info 配置生成，Agent 不推断或修改分组。
- 评分数据与 Review 数据分开处理。即使本次没有 Review，也保存成功取得的评分快照。
- 批次按评论共享组独立处理，一个组失败不阻塞其他组，允许只重试失败组。
- 同一共享组同一业务日期最多一份快照；同日重试更新当天快照，同时保留每次抓取运行记录。实际采集频率可以是一周一次或两次，并不要求每天都执行。
- 同一 Review 后续内容变化时只更新当前记录，保留首次发现和最近观察时间，不保留每次内容版本。
- 只有在完整评论列表抓取成功且连续 2 次未发现既有 Review 时，才标记为疑似移除；采集失败或结果不完整不改变评论状态。再次抓到时恢复为可见。

### 8.4 Review ID 与去重

- 优先从评论页面或 Review URL 提取稳定的来源 Review ID。
- 如果来源未提供稳定 ID，允许系统生成内部推导 ID，并标记其身份可信度较低。建议以 Marketplace、所属共享组、可获得的评论者标识/展示名、评论日期、评分、标题和正文规范化指纹生成。
- 推导 ID 不等同于 Amazon 原生 ID。正文、标题或日期变化可能造成指纹变化，进而被识别为新评论；因此不能承诺无原生 ID 时始终识别为同一条 Review。
- Reviewer ID 同样可能不可得，昵称仅作展示信息，不能作为稳定身份键。

### 8.5 建议的阶段顺序

1. **阶段 A：SKU info 关系基础。** 先实现 Father ID 的父子 ASIN 关系以及评论共享组配置所依赖的后端基础；本阶段不做评论抓取。
2. **阶段 B：评论追踪后端。** 建立共享组关联、评分快照、Review 当前记录、抓取运行记录和运营查询/维护 API。
3. **阶段 C：评论追踪页面。** 展示趋势与 Review，支持外部竞品 ASIN 和店铺临时关联管理。
4. **阶段 D：Agent API。** 提供目标读取和按共享组提交结果接口，沿用仓库现有 Agent API 认证、审计和限流模式。

各阶段的具体模型、字段、迁移和接口需在实施计划前根据现有 SKU info 数据结构验证；上述阶段为依赖顺序，不代表具体开发任务已拆分。

## 9. 再次验证 Amazon 页面字段

2026-10-12 使用 Ego 浏览器再次访问 [ASIN B0G6C865B6](https://www.amazon.com/dp/B0G6C865B6)，确认页面仍显示平均评分 2.6 / 5、7 global ratings，以及 5 星 16%、4 星 16%、3 星 15%、2 星 16%、1 星 37%。评论区可见评论者展示名称、星级、评论日期、Verified Purchase、正文；部分评论还展示 helpful votes。

本轮页面 DOM 中评论节点提供了形如 `R1F90C6R6GV8L6` 的评论标识，说明抓取端有机会从页面节点取得稳定 Review ID，即便评论标题链接未直接返回 URL。页面当前展示 6 条评论卡片，同时摘要为 7 global ratings；这再次验证评分数和页面可见文字评论数不能视为同一指标。页面评论卡片的 DOM 选择器也未可靠解析到标题字段，但页面可见文本中有标题，故采集适配应允许字段解析方式不同、字段暂缺，并将缺失与空字符串区分。

以上仅为当日页面结构的案例观察，DOM 标识是否稳定、Review ID 的可用范围以及分页完整性仍需在实际采集方案中验证。比例依然是页面原始百分比，不能据此声称精确星级数量。

## 10. 仍需后续设计确认

1. Marketplace + ASIN 的全局唯一追踪规则及一个 ASIN 同时最多属于一个有效评论共享组，是否能覆盖所有内部与外部业务场景。
2. Father ID 与现有 Project、SQ info、SKU info 记录之间的精确外键/校验关系，以及父体自身是否也作为可抓取 ASIN。
3. 一个内部共享组成员发生变化时，组的稳定身份如何保持；原组停用与新组生效的边界如何表达。
4. 评分快照缺失字段是保留上次值还是将本次字段记为空；建议将本次观测状态与历史已知值分开，避免陈旧值被误认为本次抓取结果。
5. 完整 Review 列表的判定条件、分页覆盖验证与连续 2 次缺失的计数范围（按组、按 Marketplace 和按成功完整运行）。
6. 运营页面的首版指标、筛选、排序、分页、趋势范围，以及是否需要导出或异常提醒。
7. 评论数据的合规范围、访问权限、正文保留期限及删除请求处理规则。
8. 首批 Marketplace、内部 SKU 范围和外部竞品管理权限。
