# 问题与优化建议

## 一、高优先级问题（需尽快修复）

### 1. Country Normalization 重复

- **位置**：ad_analysis_service.py、daily_analysis_service.py、product_analysis_source_service.py、inventory_analysis_service.py、product_analysis.py、payment_report_locale.py
- **问题**：国家名标准化逻辑（US/USA/美国 → US）在至少 6 处重复实现
- **影响**：新增国家支持时需修改所有 6 处，容易遗漏且维护成本高
- **建议**：提取为 `shared_utils.normalize_country()`，统一管理国家别名映射表（如 {"USA": "US", "美国": "US", "U.S.": "US"}）

### 2. 重复的 PT1 计算逻辑

- **位置**：product_analysis_script.py vs product_analysis_source_service.py
- **问题**：两处都在做 PT1 overview 计算，逻辑可能不一致
- **影响**：不同数据源计算出的 PT1 数据存在不一致风险
- **建议**：明确职责分工，script 负责从源文件计算，service 负责从数据库已存储的行重建计算

### 3. 内存任务存储（24h TTL）

- **位置**：MonthlyReportTask、AnalysisReportTask 存于模块级 dict
- **问题**：服务器重启任务丢失，无持久化，无重试机制
- **影响**：任务执行中断无法恢复，用户丢失任务进度
- **建议**：迁移至 Celery + Redis 或数据库持久化任务状态

### 4. 线程替代 Celery

- **位置**：直接使用 Thread 而非 Celery task
- **问题**：无死信队列、无重试、无任务监控
- **影响**：线程崩溃时任务静默失败，用户无法感知
- **建议**：使用 Celery 异步任务，或至少包装成可监控的 task 结构

### 5. FBA/FBM 退款计算不对称

- **位置**：monthly_report.py _sum_field
- **问题**：FBA 退款使用 "product sales" + "other"，FBM 退款只用 "product sales"
- **影响**：FBM 退款的 "other" 金额被丢弃，导致退款总额偏低
- **建议**：统一 FBA/FBM 计算逻辑，均包含 "other" 字段

## 二、中优先级问题

### 1. 汇总行检测不完整

- **位置**：product_analysis.py _is_summary_complete
- **问题**：只检查 key 存在，不检查 value 非空
- **影响**：空值会通过检测，导致后续处理空指针异常或数据错误
- **建议**：检查 value 非 None 且非空字符串

### 2. 7天广告订单假设

- **位置**：AnalysisAdProductRow.orders_7d
- **问题**：周度 PT1 使用 7 天 trailing orders，日分析可能重复计数
- **影响**：日分析中跨天广告订单被重复计算，导致数据偏高
- **建议**：日分析改用日级广告指标，或在 PT1 计算时去重

### 3. 缓存失效不完整

- **位置**：monthly_report_service.persist_monthly_report_result
- **问题**：invalidate_financial_series_cache 只传 project_id，未传 country
- **影响**：多国家场景下，缓存可能不完全失效，旧数据残留
- **建议**：传递完整的 (project_id, country) 组合作为缓存键

### 4. 事务完整性无保证

- **位置**：_persist_monthly_report
- **问题**：部分失败时不回滚已写入数据
- **影响**：数据污染，报表数据部分写入后中断
- **建议**：使用数据库事务包裹所有写入操作，失败时完整回滚

## 三、低优先级问题

### 1. _safe_div 实现不一致

- **位置**：多处
- **问题**：返回 0 / 0.0 / "0.00%" 不一致
- **影响**：前端显示格式不统一，可能出现 "NaN" 或异常字符
- **建议**：统一工具函数，规定返回值类型和格式

### 2. 库存老化计算逻辑

- **位置**：inventory_analysis_service._build_aging_status
- **问题**：90-180 天为 "aging"，181-270 天范围反而更窄
- **影响**：分类不够直观，逻辑混乱
- **建议**：重写 age bucket 定义，使区间递增合理（如 0-30/30-90/90-180/180+）

### 3. SQLite 兼容性

- **位置**：ensure_tables() 模式
- **问题**：使用 SQLite only，其他数据库依赖可能不存在的 migrations
- **影响**：切换数据库时可能遇到兼容性问题
- **建议**：统一使用 Alembic migrations，移除 SQLite 特定代码

---

## 四、可优化机会

### 性能优化

1. **索引优化**：AnalysisSourceFile.report_date 可建索引（已有 idx 但字段 nullable）
2. **Redis 缓存策略**：日分析结果可延长缓存时间，减少重复计算
3. **N+1 查询**：daily_analysis_service 批量加载优化，避免循环内查询

### 代码复用

1. Country normalization → shared_utils
2. _safe_div → shared_utils
3. 内存任务存储 → Celery

### 可扩展方向

1. 更多国家支持（扩展 payment_report_locale）
2. 自动化调度（Celery beat periodic tasks）
3. 更多报表类型（税务报告等）
