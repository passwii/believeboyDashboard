# 数据库安全（现状问题与整改）

> 更新时间：2026-02-25
> 范围：`/frontend` + `/backend` 当前实现

## 结论摘要

当前项目的数据访问主链路总体正确：前端页面通过 HTTP 调用后端 API，数据库写入主要在后端完成。

但存在一个高优先级问题：前端使用 `NEXT_PUBLIC_BACKEND_API_KEY` 作为后端鉴权凭证。该变量会暴露在浏览器端 bundle 中，不应作为安全边界。

## 当前已确认的问题

### P0：后端 API Key 通过前端公开变量下发（高风险）

- 现状
  - 前端页面读取 `NEXT_PUBLIC_BACKEND_API_KEY`，并在请求头写入 `X-API-Key`。
  - 后端依赖 `X-API-Key` 做接口保护。
- 证据位置
  - `frontend/app/dashboard/data-analysis/daily-report/page.tsx`
  - `frontend/app/dashboard/data-management/sku-cost/page.tsx`
  - `backend/app/core/security.py`
  - `frontend/.env.example`
- 风险说明
  - `NEXT_PUBLIC_*` 变量会进入浏览器可见代码，任何用户都可提取。
  - 一旦 key 泄露，攻击者可伪造前端请求直接调用受保护接口。

### P1：数据库/服务端密钥目前放在 frontend 环境文件（中风险）

- 现状
  - `frontend/.env.local` 中包含 `SUPABASE_SECRET_KEY`、`SUPABASE_DB_PASSWORD` 等服务端敏感变量。
- 风险说明
  - 虽然 `.env.local` 已被忽略，不会默认入库，但位置在 `frontend` 目录，团队协作中容易误用到客户端代码。
  - 若后续误改为 `NEXT_PUBLIC_*` 或被日志/构建脚本输出，会形成泄露。

## 非问题项（避免误判）

### `migrations` 在 frontend 目录不是本质问题

- 现状
  - 迁移与导入脚本通过 Node 命令执行（`pnpm db:migrate:product-costs` / `pnpm db:import:product-costs`）。
- 结论
  - 只要这些脚本仅在本地 CLI/CI/服务端执行，不在浏览器执行，就是可接受的工程组织方式。

## 最小整改方案（按优先级）

1. 移除 `NEXT_PUBLIC_BACKEND_API_KEY` 的使用。
2. 改为服务器中转：浏览器 -> Next 服务端路由（或后端登录态）-> FastAPI。
3. 将后端凭证改为非公开变量名（例如 `BACKEND_API_KEY`），仅在服务端读取。
4. 轮换当前后端 API key（因为历史上已以公开变量方式使用过）。
5. 将 `SUPABASE_SECRET_KEY`、数据库密码统一收敛到服务端环境（优先 backend 侧），前端目录只保留公开变量与非敏感配置。

## 验收标准

- 前端构建产物中不再出现后端 API key 字符串。
- 浏览器网络请求中不再携带固定 `X-API-Key`。
- 后端仍可正常鉴权，但凭证仅在服务端可见。
- 迁移/导入脚本可继续执行，且不依赖浏览器端环境。

## 备注

本文件仅记录当前已确认风险，不替代完整安全审计（如账号体系、RLS 策略、防火墙、速率限制、审计日志）。
